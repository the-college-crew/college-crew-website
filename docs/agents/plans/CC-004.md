# CC-004 — Give provider profile pages real metadata and Service structured data

**Status:** approved
**Owner:** Zach
**Branch:** none yet
**Updated:** 2026-08-02

## Goal

Every provider profile page currently ships the identical
`{ title: "Provider profile" }` regardless of who the provider is, and the app
has zero `application/ld+json` anywhere. Done looks like: each
`/providers/[id]` page has a per-provider `<title>`, a real meta description,
a canonical URL, and a `Service` JSON-LD block (with `aggregateRating` when
the provider has reviews) — so the pages `app/sitemap.ts` already lists as
indexable actually carry the on-page signals search engines and AI answer
engines use. Purely additive: no visual change to the rendered page, no data
mutation, no schema change.

## Files to change

- `apps/web/app/(customer)/providers/[id]/page.tsx` — replace the static
  `export const metadata` with `export async function generateMetadata`, and
  add a JSON-LD `<script>` tag to the page body using the `provider` object
  the page already fetches.

That's the only file. Everything the metadata and JSON-LD need — rating,
services, town, provider type, avatar path — is already returned by
`getPublicProviderProfile` in `apps/web/lib/db/queries.ts` (see
`PublicProviderProfile` / `ProviderCard`, `lib/db/queries.ts:58-83`). No other
file needs to change.

## Approach

1. Add a `SITE_URL` constant at the top of `page.tsx`, matching the exact
   fallback string already used in `apps/web/app/sitemap.ts:5` and
   `apps/web/app/robots.ts:3-4`:
   `process.env.NEXT_PUBLIC_SITE_URL || "https://www.thecollegecrew.com"`.
   (There's no shared `lib/url.ts` — both existing call sites duplicate this
   constant locally, so match that precedent rather than introducing a new
   shared module for one more usage.)

2. Replace the static `metadata` export with:

   ```ts
   export async function generateMetadata({
     params,
   }: {
     params: Promise<{ id: string }>;
   }): Promise<Metadata> {
     const { id } = await params;
     const provider = await getPublicProviderProfile(id, null);
     if (!provider) return { title: "Provider not found" };

     const displayName = provider.company_name || provider.display_name;
     const primaryService = provider.services[0]?.service.name;
     const title = primaryService
       ? `${displayName} — ${primaryService} in ${provider.town} | College Crew`
       : `${displayName} | College Crew`;
     const description = provider.bio
       ? provider.bio.slice(0, 155)
       : `${displayName} offers ${provider.services.map((s) => s.service.name).join(", ") || "home services"} in ${provider.town} on College Crew.`;

     return {
       title,
       description,
       alternates: { canonical: `${SITE_URL}/providers/${id}` },
     };
   }
   ```

   This is the same "fetch once for metadata, fetch again for the page body"
   shape already used in `apps/web/app/(customer)/blog/[slug]/page.tsx:28-38`
   — no new caching pattern, see Out of scope.

3. In the page component, after the existing `if (!provider) notFound();`
   guard, build a plain object for the JSON-LD block:

   ```ts
   const serviceSchema = {
     "@context": "https://schema.org",
     "@type": "Service",
     name: provider.company_name || provider.display_name,
     areaServed: provider.town,
     provider: {
       "@type": provider.provider_type === "business" ? "Organization" : "Person",
       name: provider.company_name || provider.display_name,
     },
     ...(provider.rating
       ? {
           aggregateRating: {
             "@type": "AggregateRating",
             ratingValue: provider.rating.avg,
             reviewCount: provider.rating.count,
           },
         }
       : {}),
     offers: provider.services.map((offered) => ({
       "@type": "Offer",
       name: offered.service.name,
       priceCurrency: "USD",
       ...(offered.pricing_mode === "hourly" && offered.hourly_rate_cents != null
         ? { price: (offered.hourly_rate_cents / 100).toFixed(2) }
         : {}),
     })),
   };
   ```

   `provider.provider_type` is `"business" | "individual"`
   (`lib/db/types.ts:3652`) — same field `components/provider-profile.tsx:96-99`
   already branches on for the "Student business" / "Hardworking individual"
   badge, so this reuses an existing distinction rather than inventing one.

4. Render it in the returned JSX, next to the existing `<ProviderProfile>`:

   ```tsx
   <script
     type="application/ld+json"
     dangerouslySetInnerHTML={{
       __html: JSON.stringify(serviceSchema).replace(/</g, "\\u003c"),
     }}
   />
   ```

   The `.replace(/</g, ...)` is required, not decorative: `JSON.stringify`
   never escapes `<`, and an admin-approved but attacker-influenced
   `company_name`/`bio` containing `</script>` would otherwise break out of
   the script tag. This is the standard Next.js idiom for inline JSON-LD.

## Schema impact

None. No migration, no new table or column read — every field used already
comes back from `getPublicProviderProfile`.

## How to verify

- Run a build (`npm run build` from `apps/web`, per `CLAUDE.md`'s note that
  `next-env.d.ts` requires a build before typecheck/tsc can pass on a fresh
  clone) and start the app, or check a Preview deploy.
- Load `/providers/<a real approved provider id>` and view source:
  - `<title>` should contain that provider's name and service, not the
    literal string "Provider profile".
  - A single `<script type="application/ld+json">` block should be present;
    copy its contents and confirm `JSON.parse` succeeds (or paste into
    Google's Rich Results Test).
  - If that provider has zero reviews, confirm `aggregateRating` is absent
    from the JSON rather than present with `null` values (`provider.rating`
    is `null` when `mapRating` sees no rating row — `lib/db/queries.ts:274-277`).
- Load `/providers/does-not-exist`: confirm the page still 404s via the
  existing `notFound()` call, and that `generateMetadata` doesn't throw for a
  missing id (returns the `{ title: "Provider not found" }` fallback).
- Confirm `apps/web/app/robots.ts` and `apps/web/app/sitemap.ts` are
  untouched — this plan changes per-page signals only, not what's indexed.

## Out of scope

- No change to the visual rendering in `components/provider-profile.tsx`.
- No site-wide `Organization` schema, no `BreadcrumbList`, no JSON-LD on the
  homepage or Browse page — provider profile pages only, per the backlog item.
- No `cache()`-wrapped data-fetching refactor to dedupe the
  `generateMetadata`/page-body double fetch. `blog/[slug]/page.tsx` already
  accepts this duplicate-fetch shape without it, and CC-005 was just rejected
  for adding caching to a read that isn't a measured bottleneck at 6
  providers — same reasoning applies here.
- No Open Graph / Twitter card image using `providerAvatarUrl` — not asked
  for by the backlog item (see Risks below).

## Risks and open questions

- The backlog text says `aggregateRating` should be "sourced from the rating
  data `lib/browse/ranking.ts` already computes." That's not quite right:
  `ranking.ts` only *consumes* an `avgRating`/`reviewCount` pair for scoring —
  it doesn't compute or store the rating itself. The actual source is
  `provider.rating` (built by `mapRating` over the `provider_ratings` view in
  `lib/db/queries.ts:274-277`), already returned by `getPublicProviderProfile`.
  This plan uses that field directly; flagging the discrepancy so it isn't
  read as a missed import.
- `"@type": "Organization"` for `provider_type === "business"` is a judgment
  call — these are hyperlocal student businesses without a public street
  address, so `LocalBusiness` (which schema.org expects to carry an address)
  seemed like a worse fit than a plain `Organization`. No precedent for this
  exists elsewhere in the codebase; Zach should confirm before this ships if
  he has a preference.
- Whether to also add `openGraph`/`twitter` image metadata via
  `providerAvatarUrl(provider.avatar_image_path)` while this file is already
  open — left out because the backlog item didn't ask for it, but worth a
  yes/no from Zach since the marginal cost of adding it now is small.
