## CC-006 and CC-007 are done, not buildable — a process gap, corrected this run

Both show `**Status:** approved` in `backlog.md` on `main`, which on its face
looks buildable. They are not: both were fully built last night (2026-08-04)
and are sitting in open PRs — #172 (CC-006) and #173 (CC-007) — each of whose
body says explicitly *"Complete. `npm run build`/`lint`/`typecheck` all pass
... Backlog status set to `in-progress`"*. Per `docs/agents/README.md`'s "Work
must survive a dead session" section: *"the PR description says the work is
complete → finished, just awaiting Zach's merge. Leave it alone."* Building
either again would open a duplicate PR for the same change.

**Why `backlog.md` on `main` didn't already say `in-progress`:** last night's
Worker bundled the `in-progress` status edit into the *same commit* as the
code change, on the code branch — so the status update only reaches `main`
when Zach merges the code PR, not when the Worker opens it. That defeats the
whole point of the status field: a zero-context Worker reading `main` mid-wait
sees `approved` and cannot tell "never touched" from "built, awaiting merge"
apart without separately checking every open PR's body text.

**Fixed this run:** pushed the `in-progress` status for both items as part of
this same docs-only commit (see `## Slack` below and the diff on this PR) —
correcting `backlog.md` to match reality immediately, independent of when the
code PRs merge. Going forward, the status edit for a new item should ship as
its own self-mergeable docs-only push at the time the code PR opens, not
bundled into the code branch — flagging this so a future Planner/Worker reads
it before repeating the same gap.
