## CC-006 and CC-007 are done, not buildable — a process gap, corrected this run

Both showed `**Status:** approved` in `backlog.md` on `main` at the start of
this run, which on its face looks buildable. They are not: both were fully
built last night (2026-08-04) and are sitting in open PRs — #172 (CC-006) and
#173 (CC-007) — each of whose body says explicitly *"Complete.
`npm run build`/`lint`/`typecheck` all pass ... Backlog status set to
`in-progress`"*. Per `docs/agents/README.md`'s "Work must survive a dead
session" section: *"the PR description says the work is complete → finished,
just awaiting Zach's merge. Leave it alone."* Building either again would
have opened a duplicate PR for the same change.

**Why `backlog.md` on `main` didn't already say `in-progress`:** last night's
Worker bundled the `in-progress` status edit into the *same commit* as the
code change, on the code branch — so the status update only reaches `main`
when Zach merges the code PR, not when the Worker opens it. That defeats the
whole point of the status field: a zero-context Worker reading `main` mid-wait
sees `approved` and cannot tell "never touched" from "built, awaiting merge"
apart without separately checking every open PR's body text.

**Fixed this run**, via PR #190 (self-merged, docs-only): corrected both
items to `in-progress — PR #<n> open, awaiting Zach's merge`, independent of
whether the code PRs have merged yet. Flagging for whoever plans or builds
next: ship a status-field edit as its own self-mergeable docs-only push at
the moment a code PR opens, not bundled into the code branch, so `main`
never lags reality on this again.
